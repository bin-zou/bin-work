
## 引言

第一章已经解决了“为什么需要RTOS”的问题。随着系统中的功能越来越多，程序从简单循环发展到超级循环、轮询和中断，最后把不同功能拆成多个Task，并把“现在到底让谁运行”的问题交给RTOS。第二章就是紧接着回答这个问题：当系统中已经存在多个Task，而CPU在同一时刻通常只能执行一个Task时，RTOS究竟按照什么规则决定谁运行、谁等待、谁被打断，以及这种调度机制在程序内部是怎样实现的。

因此，第二章的核心不是单独记住“优先级、时间片、TCB、Tick”等术语，而是理解一条逐步发展的逻辑：最开始可以让任务按固定顺序合作执行；当任务数量增加以后，可以给每个任务固定的一段CPU时间；但不同任务的重要程度并不一样，因此进一步引入优先级；当高优先级任务变得可以运行时，如果还必须等待低优先级任务主动让出CPU，实时性仍然不足，于是发展出基于优先级的抢占式调度；为了真正实现这种调度，内核还必须记录每个Task的状态、优先级、栈和运行位置，这就引出了任务队列、TCB、Tick和上下文切换等实现机制。

这一章可以沿着这样的逻辑理解：合作调度解决“多个Task轮流执行”的问题，时间分片解决“一个Task不能长期霸占CPU”的问题，优先级解决“不同Task重要程度不同”的问题，抢占解决“紧急Task不能等低优先级Task做完”的问题，而TCB、任务队列和Tick解决“RTOS怎样把这些规则真正运行起来”的问题。

## 从第一章进入第二章：Task并不是“运行一次就结束”

在普通顺序程序中，我们很容易形成一种思维：一个函数开始执行，等它执行结束以后，再执行下一个函数。例如：

```c
A();
B();
C();
```

这里确实是A执行完以后才进入B，B执行完以后再进入C。但是RTOS中的Task通常不是这种“执行一次就结束”的函数。一个典型Task往往具有自己的循环：

```c
void CurrentTask(void)
{
    while(1)
    {
        CurrentControl();
        WaitNextPeriod();
    }
}
```

因此一个Task可能从系统启动一直存在到系统关闭，它不会因为完成了一次电流控制就真正消失。它更常见的运行过程是“运行一小段，然后等待；条件满足以后再次变成可以运行；再被调度器选中运行”。

所以第二章研究的并不是“一个Task结束以后选择谁”，而是“当前Task什么时候继续占用CPU，什么时候主动让出CPU，什么时候会被其他Task抢占，以及让出CPU以后下一步选择谁”。

这里需要重新理解Running。Running只是表示“这个Task此刻正在使用CPU”，并不表示“这个Task必须运行到整个任务结束”。在抢占式RTOS中，一个Running状态的Task完全可能在代码执行到一半时被暂停，然后以后再从原来的位置继续运行。

## 合作调度：最简单的Task调度思想

当系统刚刚从超级循环进入任务化以后，最容易理解的方式是合作调度。所谓合作调度，可以把它理解为“大家轮流使用CPU，但是正在运行的Task必须自己主动把CPU交出来”。

例如系统有三个Task：

```c
void TaskA(void)
{
    while(1)
    {
        DoA();
        Yield();
    }
}

void TaskB(void)
{
    while(1)
    {
        DoB();
        Yield();
    }
}

void TaskC(void)
{
    while(1)
    {
        DoC();
        Yield();
    }
}
```

这里的 `Yield()` 可以先理解为“我这一次工作做完了，CPU可以先给别人”。调度器可能形成这样的执行关系：

```text
TaskA运行一段
→ TaskA主动让出CPU
→ TaskB运行一段
→ TaskB主动让出CPU
→ TaskC运行一段
→ TaskC主动让出CPU
→ 再回到TaskA
```

合作调度和第一章的超级循环很像，但两者并不完全相同。超级循环是程序员直接把A、B、C写成固定的函数调用顺序，而合作调度已经把A、B、C抽象成了独立Task，内核开始参与任务切换和状态管理。只是这时候调度器还比较“客气”，它不会随便把正在Running的Task强行赶下CPU，而是等待这个Task主动让出。

餐馆中可以把它理解成几个工作轮流使用同一个厨师。厨师先做一会儿炒饭，炒饭任务自己说“这一阶段完成了，可以先去做别的”，于是厨师去煮面；煮面做到一个合适节点后也主动让出，厨师再去处理外卖。大家能够合作，所以整个厨房可以运行。

这种方法的优点是简单。因为Task只会在自己主动让出CPU的位置发生切换，程序员比较容易知道哪里可能发生任务切换，共享数据的分析也相对容易。例如一段关键代码中间没有 `Yield()`、等待操作或其他主动让出CPU的行为时，通常不会突然被另一个普通Task从中间抢走。

但是它有一个根本问题：系统实时性高度依赖每个Task是否“自觉”。假设TaskB写成：

```c
void TaskB(void)
{
    while(1)
    {
        VeryLongCalculation();
    }
}
```

它一直不调用等待、延时或 `Yield()`，那么它可能长期占据CPU。即使TaskA非常紧急，已经具备运行条件，也只能等TaskB主动交出CPU。对于简单、任务之间高度合作、实时要求不高的系统，这种方式可以使用；但对于严格实时控制，如果某个低重要性的Task能够长时间挡住重要Task，就会产生严重问题。

所以合作调度不能很好解决的问题是：如果一个Task不主动让出CPU，其他更重要的Task怎么办。

## 周期循环：让Task按照时间节奏运行

嵌入式控制系统中很多Task不是“有空就运行”，而是具有明确周期。例如电流控制每100 μs运行一次，位置控制每1 ms运行一次，通信状态处理每10 ms运行一次。因此调度器不仅需要知道“谁可以运行”，还要知道“什么时候到它的运行时刻”。

一个周期Task可以抽象成：

```c
void CurrentTask(void)
{
    while(1)
    {
        CurrentControl();
        DelayUntilNextPeriod();
    }
}
```

`DelayUntilNextPeriod()` 的意义不是让CPU停下来等待，而是告诉RTOS：“我这一周期的工作完成了，在下一周期到来以前不用再给我CPU。”于是CurrentTask进入等待状态，CPU可以运行其他Task。下一周期到来时，RTOS再把它变成Ready。

例如电流控制周期为100 μs，那么可以理解为：

```text
0 μs：CurrentTask运行
运行20 μs以后完成本周期控制
20~100 μs：CurrentTask等待
100 μs：下一周期到来，重新Ready
```

这与忙等待完全不同。如果写成：

```c
while(CurrentTime < NextPeriod)
{
}
```

那么CPU会一直耗在这里等时间到；而RTOS周期等待是Task自己暂时退出CPU竞争，让其他Task利用这段时间。

周期循环解决了“不同任务具有不同时间节奏”的问题，但它仍然没有完全解决“多个Task同时想运行时应该选谁”的问题。因此还需要进一步的调度规则。

## 时间分片：防止一个Task长期占用CPU

时间分片调度的核心思想是：即使一个Task自己不主动让出CPU，系统也只允许它连续运行一段有限时间，时间到了以后切换给其他Task。

这里的“时间片”可以理解为RTOS分配给某个Task的一小段CPU使用时间。例如TaskA、TaskB、TaskC具有相同优先级，每个Task获得5 ms时间片，那么执行过程可能是：

```text
TaskA运行5 ms
→ TaskB运行5 ms
→ TaskC运行5 ms
→ 再回到TaskA
```

餐馆中可以理解为一个厨师同时处理几个同等重要的订单。厨房主管规定，每个订单先处理两分钟，两分钟以后如果还没有做完就先暂停，去处理下一个订单，之后再回来继续。这样可以避免某个订单长期霸占厨师。

时间分片的优点是公平。对于同等重要、都需要持续计算的任务，能够避免一个Task长期占据CPU。它在通用操作系统中非常常见，因为桌面系统往往希望很多程序都能“感觉自己在同时运行”。

但实时系统只强调公平是不够的。假设DisplayTask正在使用自己的时间片，而CurrentTask已经到达100 μs控制周期。如果两者还要公平地一人一片时间，那么关键控制Task可能因为等待时间片而错过Deadline。因此时间分片能够解决“CPU使用公平性”，却不能单独解决“不同Task实时重要程度不同”的问题。

这就引出了优先级。

## 优先级：不同Task并不是同样重要

实时系统的核心特点之一是不同Task的时间要求不同。例如：

```text
CurrentTask：必须很快执行
PositionTask：稍慢一些也可以
CommunicationTask：允许更长响应时间
DisplayTask：晚几十毫秒通常也没有问题
```

因此RTOS会给Task设置Priority，即优先级。优先级表示的是调度意义上的“谁更应该先获得CPU”，而不是这个功能在整个工程中是否重要。

例如可能设定：

```text
CurrentTask         高优先级
PositionTask        较高优先级
CommunicationTask   中优先级
DisplayTask         低优先级
```

当多个Task同时处于Ready状态时，基于优先级的调度器会优先选择更高优先级Task运行。

这里的Ready需要特别区分。Ready表示“任务已经具备运行条件，只是在等CPU”；Running表示“任务当前真的正在使用CPU”；Blocked表示“任务正在等待某个条件，即使现在给CPU也没有意义”。

例如UARTTask正在等待数据时是Blocked。UART数据到达以后，它不一定马上Running，而是先从Blocked变成Ready。如果此时还有更高优先级Task正在运行，UARTTask仍然需要在Ready状态等待。

优先级解决了“多个Task同时可以运行时谁更重要”的问题，但如果系统采用的仍然是合作式调度，一个高优先级Task虽然Ready了，却仍然可能等待当前低优先级Task主动让出CPU。因此，仅仅有优先级还不等于真正的快速实时响应。

## 基于优先级的抢占式调度：高优先级Task可以打断低优先级Task

这正是前面最容易产生疑问的地方。在典型抢占式RTOS中，如果一个低优先级Task正在Running，而更高优先级Task突然变成Ready，调度器可以暂停当前Task，立即让更高优先级Task获得CPU。

例如：

```text
DisplayTask：低优先级，当前Running
CurrentTask：高优先级，当前Blocked，等待下一控制周期
```

当100 μs控制周期到达以后：

```text
CurrentTask：Blocked → Ready
```

此时调度器发现CurrentTask优先级高于DisplayTask，于是：

```text
DisplayTask正在运行
→ 保存DisplayTask的运行现场
→ DisplayTask暂时停止
→ 恢复CurrentTask的运行现场
→ CurrentTask开始Running
```

CurrentTask完成本周期控制以后再次等待下一周期：

```text
CurrentTask：Running → Blocked
```

调度器重新检查Ready队列，如果此时DisplayTask仍然是可以运行的最高优先级Task，就恢复DisplayTask。DisplayTask不是重新从头运行，而是从刚刚被暂停的位置继续。

餐馆中可以理解为厨师正在擦桌子，突然锅里的油开始冒烟。厨房主管不会让厨师“把桌子擦完再去关火”，而是让擦桌子的工作立刻暂停，先处理冒烟的锅，危险处理完以后再回来继续擦桌子。擦桌子的完成时间被推迟了，但更紧急事情的响应时间得到了保证。

这就是Preemption，即抢占。抢占的本质并不是让所有Task都更快，而是允许系统牺牲低优先级Task的一部分及时性，换取高优先级Task更快获得CPU。

## 抢占会不会让数据乱

Task可以在Running过程中被暂停，因此自然会产生一个问题：如果两个Task共同访问同一份数据，会不会因为一个Task执行到一半被另一个Task抢占而导致数据不一致。

答案是会有这种风险，但“Task被抢占”本身不会自动把Task自己的运行现场弄丢。RTOS在上下文切换时会保存必要的CPU状态，包括当前执行位置、栈指针和寄存器等，使Task以后能够从原来的位置继续执行。

真正危险的是共享数据。例如：

```c
count++;
```

从C语言看只有一句，但CPU内部可能需要经历“读取count、加1、写回count”。假设TaskB读取到 `count = 10` 后被TaskA抢占，TaskA也执行一次 `count++` 并写回11。TaskB恢复以后仍然基于自己之前读到的10计算，再写回11。这样两个Task各加一次，最终却只得到11，而不是12。

这种最终结果依赖于多个执行流恰好以什么顺序交叉执行的现象叫Race Condition，即竞态条件。

因此，抢占式调度提高实时性的同时，也使共享资源保护变得更加重要。第二章先让我们意识到这个问题，而第三章会正式研究互斥机制、信号量和互斥量等解决方法。

这里也需要特别注意 `volatile`。`volatile` 主要告诉编译器某个变量可能在当前代码之外发生变化，不要随意把访问优化掉；它并不能保证 `count++` 变成不可打断的操作，因此 `volatile` 不等于原子操作，也不等于线程安全。

## 上下文切换：为什么Task能够执行到一半再回来

当调度器把CPU从TaskB切换到TaskA时，不可能简单地“忘掉TaskB”。否则以后根本不知道TaskB刚才执行到了哪里。

因此RTOS需要保存TaskB的Context，即上下文。这里可以把上下文理解成“CPU继续执行这个Task所必须保存的现场”。

概念上包括程序执行位置、CPU寄存器、栈指针和部分处理器状态。然后RTOS恢复TaskA之前保存的上下文，让CPU继续执行TaskA。

这个过程叫Context Switch，即上下文切换。

可以把它想象成厨师正在按照一张复杂配方做菜，做到第三步时突然需要去处理另一道菜。为了回来以后能够继续，必须记录“刚刚做到第三步、锅里温度多少、已经加入了什么材料”。处理完另一件事情以后，再按照这个记录恢复原来的工作。

上下文切换并不是免费的。保存当前Task状态、选择下一个Task、恢复下一个Task状态都会消耗CPU时间。因此抢占并不是越频繁越好。一个系统如果不断发生Task切换，CPU就可能花很多时间在“切换谁运行”，而不是实际执行控制算法。

这部分时间称为调度开销或上下文切换开销。实时系统设计时要保证它相对于任务周期足够小，并且具有较好的确定性。

## 任务队列：调度器怎样知道有哪些Task可以运行

当Task数量增加以后，调度器不能每次都漫无目的地搜索整个系统。RTOS通常会按照Task状态和优先级把任务组织起来，其中最重要的是Ready任务的管理。

可以把Ready Queue理解成“已经具备工作条件、正在排队等CPU的一组Task”。

例如：

```text
CurrentTask       Ready
PositionTask      Ready
UARTTask          Blocked
DisplayTask       Ready
```

UARTTask因为还在等待数据，不应该参加CPU竞争。调度器只需要从Ready任务中按照调度规则选择一个。

如果采用优先级抢占式调度，那么核心逻辑可以简化为：

```text
从Ready任务中
找到最高优先级Task
→ 让它Running
```

当某个Task因为等待数据、等待时间或等待资源进入Blocked以后，它会从Ready集合中离开；当等待条件满足时，再重新加入Ready集合。

这里的Queue即队列，可以先理解为RTOS用来有组织地保存一组等待处理对象的数据结构。第二章中的“使用队列”主要是为了让后面的任务管理实现变得具体：调度器不是凭空知道Task状态，而是通过内核维护的数据结构来管理它们。

## TCB：RTOS必须给每个Task建立一份“档案”

只知道系统中存在一个 `CurrentTask()` 函数还不够。RTOS要完成抢占和恢复，必须知道这个Task当前是什么状态、优先级是多少、栈在哪里、刚才运行到了什么位置等。

因此内核通常为每个Task建立一份控制信息，这就是TCB。

TCB是Task Control Block，即任务控制块。可以把它理解成RTOS为每个Task建立的一张“任务档案卡”。

这张档案卡中通常会保存与任务管理有关的信息，例如任务当前状态、任务优先级、任务栈指针、任务标识以及用于挂入各种任务队列的链接信息。不同RTOS的TCB字段会有所不同，但核心作用相同：RTOS通过TCB知道“这个Task是谁、现在在哪里、下一次怎样继续运行”。

例如调度器决定暂停DisplayTask时，需要先把它当前的栈指针等信息记录到DisplayTask对应的TCB；以后重新运行DisplayTask时，再根据TCB找到它之前保存的现场。

所以可以简单理解：Task是“实际要做的工作”，TCB是“RTOS记录这项工作状态的档案”。

## 进程描述符：操作系统为什么还需要更多任务信息

书中还会引入Process Descriptor，即进程描述符。对于当前学习阶段，不需要马上把Task、Thread和Process全部混在一起。

可以先抓住共同思想：只要操作系统需要管理一个可以独立执行的对象，就必须在内核中保存一组描述它的信息。对于Task，可以有TCB；对于更完整的Process，操作系统还需要记录地址空间、资源、打开的对象等更多信息，因此会有相应的进程描述结构。

在小型嵌入式RTOS中，Task往往是最核心的调度单位，因此TCB尤其重要。到了更完整的通用操作系统中，Process和Thread的区分会更加明显。第二章在这里主要是让我们认识：操作系统管理“任务”并不是只保存一个函数地址，而是必须维护一个完整的软件对象描述。

## Tick：RTOS怎样知道“时间到了”

周期Task需要每100 μs、1 ms或者10 ms运行一次，那么RTOS必须有某种时间基准来判断“现在过去了多久”。

传统RTOS中常见的方法是System Tick，即系统节拍。可以把Tick理解为操作系统内部的一只周期性电子钟。

例如系统设置：

```text
1 Tick = 1 ms
```

定时器每1 ms产生一次节拍事件：

```text
Tick 1
Tick 2
Tick 3
Tick 4
……
```

RTOS根据Tick计数就能够实现诸如“TaskA延时10个Tick”“TaskB每100个Tick运行一次”等时间管理。

例如：

```c
Delay(10);
```

如果一个Tick是1 ms，那么可以粗略理解为当前Task请求等待约10 ms。Task进入Blocked，RTOS记录它还需要等待多少个Tick。随着系统Tick不断到来，等待计数逐渐减少，到期以后Task由Blocked变成Ready。

Tick解决的是操作系统内部统一的时间基准问题，但也会带来精度和开销问题。如果一个Tick是1 ms，那么很多时间事件只能以1 ms左右的粒度表达；如果把Tick提高到10 μs，时间分辨率更高，但系统会更频繁地处理Tick，增加CPU开销。

因此Tick不是越快越好，而是需要在时间分辨率和系统开销之间折中。后续不同RTOS还可能使用Tickless等方式减少无意义的周期Tick，但当前阶段先理解“Tick是RTOS管理时间的一种基础节拍”即可。

## 优先级与系统响应速度

优先级真正影响的是“一个Task变成Ready以后，要等多久才能得到CPU”。

假设低优先级DisplayTask正在运行，高优先级CurrentTask到期变成Ready。如果采用优先级抢占式调度，CurrentTask可以很快抢占DisplayTask，因此它的响应时间很短。

但这并不意味着“把所有Task优先级都设得很高”就能提高整个系统性能。优先级是相对关系，不可能所有Task都比别人更高。更重要的是，高优先级Task运行期间会推迟低优先级Task，因此优先级分配本质上是在决定“当CPU不够同时服务所有任务时，谁可以等待，谁不能等待”。

例如电机控制系统中，100 μs电流控制Task通常比100 ms数据显示Task更强调及时性，因此更高优先级具有合理性。如果反过来让显示Task长期压住电流控制Task，即使显示界面非常流畅，控制系统也可能失去实时性。

所以实时调度的目标不是让所有Task平均公平，而是根据不同Task的时间约束，使真正有Deadline要求的Task能够及时执行。

## 绕过调度器：为什么有时不能让调度器随时切换Task

抢占式调度虽然能够提高高优先级Task的响应能力，但某些非常短的关键操作中，我们可能暂时不希望发生任务切换。

例如内核正在修改某个与任务队列相关的数据结构，如果修改到一半就切换到另一个Task，而另一个Task又访问同一结构，就可能造成数据损坏。因此某些RTOS会提供短暂锁住调度器、进入临界区或使用其他方式阻止特定切换的机制。

这里的思想不是“抢占不好，所以把抢占关掉”，而是“在少数必须保持操作完整性的短时间内，暂时禁止某些调度行为”。

这种做法必须非常谨慎。假设高优先级CurrentTask已经Ready，但低优先级Task长时间锁住调度器，那么高优先级Task仍然不能获得CPU，实时性就会下降。因此绕过或锁住调度器的代码必须尽量短，而且应当清楚知道为什么需要这样做。

这与前面讲的中断屏蔽类似：它们都可以保护关键操作，但保护时间过长就会转化为实时延迟。

## 代码共享与重入：同一个函数能不能被多个Task同时使用

多个Task可能调用同一个函数，例如：

```c
float Limit(float x)
{
    if(x > 1.0f) return 1.0f;
    if(x < -1.0f) return -1.0f;
    return x;
}
```

这种函数只使用输入参数和自己的局部变量，TaskA调用到一半被TaskB抢占，TaskB也调用 `Limit()`，通常不会彼此破坏。TaskB执行完成以后，TaskA仍然可以继续。这类能够被多个执行流交叉调用而不会破坏结果的代码具有Reentrant，即可重入性。

可重入可以先理解为：“同一个函数执行到一半时，即使另一个Task再次进入这个函数，也不会因为共享内部状态而把前一次调用的数据弄乱。”

但如果函数使用共享的静态变量或全局临时变量，就可能不可重入。例如：

```c
int Calc(void)
{
    static int temp;

    temp = ReadA();
    temp = temp + 1;

    return temp;
}
```

TaskA执行到 `temp = ReadA()` 后被TaskB抢占，TaskB重新进入 `Calc()` 并修改同一个 `temp`，TaskA回来以后读到的就可能已经不是自己的中间结果。

因此抢占式多任务系统中，不仅共享全局数据需要保护，共享代码本身是否可重入也需要考虑。

这里的核心不是“多个Task不能调用同一个函数”，而是要判断这个函数内部有没有多个调用者共同修改的状态。

## 运行时行为为什么会变得不可预测

顺序程序最大的优点之一是执行路线容易理解：

```text
A结束
→ B
→ C
```

进入抢占式RTOS以后，执行顺序可能变成：

```text
TaskB运行
→ TaskA变成Ready
→ TaskB被抢占
→ TaskA运行
→ TaskA等待
→ TaskB恢复
→ 又有TaskC变成Ready
→ 再次切换
```

如果不同Task又在共享数据、等待资源、响应中断，那么程序实际运行顺序会比裸机顺序程序复杂得多。

这里的“不可预测”不能简单理解为RTOS一定没有规律，而是说仅仅看某一段C代码已经不能直接判断系统实际执行顺序，因为执行过程还受到Task优先级、Ready/Blocked状态、外部事件、中断和调度时刻等因素影响。

RTOS真正追求的是把这种复杂性变成“有规则、可分析的复杂性”。例如虽然我们不知道UART数据具体哪一微秒到达，但我们知道UARTTask被唤醒以后会进入Ready；如果它是最高优先级Ready Task，调度器会让它抢占低优先级Task。这样就能够分析最坏响应时间。

因此实时系统的目标并不是让执行顺序重新变成绝对固定，而是让调度规则足够明确，使系统时间行为能够被分析和约束。

## 第二章中的Task应该怎样整体理解

经过这一章以后，Task不能再只被理解成“一个函数”。一个Task实际上同时具有功能和运行状态。

从功能角度，它负责某项工作，例如电流控制或通信解析；从调度角度，它还有优先级、状态、栈和上下文等信息。它可能处于Running、Ready或者Blocked，并且这些状态会随着时间和事件不断变化。

一个典型周期Task的生命周期可以理解为：

```text
下一周期到来
→ Blocked变成Ready
→ 调度器选中
→ Ready变成Running
→ 执行本周期工作
→ 等待下一周期
→ Running变成Blocked
```

如果它运行过程中更高优先级Task变成Ready：

```text
当前Task Running
→ 被抢占
→ 当前Task变回Ready
→ 高优先级Task Running
→ 高优先级Task后来Blocked
→ 原Task重新Running
```

所以Ready与Blocked的区别特别重要。Ready是“我能运行，只是没拿到CPU”；Blocked是“我现在不能继续，即使CPU空闲也没意义”。

## 餐馆例子串起整个第二章

可以继续沿用第一章的餐馆模型。第一章结束时，餐馆已经有多个工作，而且安排了一个厨房主管，相当于RTOS调度器。第二章研究的就是这个主管究竟怎样安排厨师。

最简单时，主管让各项工作互相配合，当前工作自己说“这一阶段做完了”，厨师再去做下一项，这就是合作调度。后来发现有些工作一直做不完，于是主管规定每项工作只能连续占用厨师一小段时间，时间到了换下一项，这就是时间分片。

再后来发现“擦桌子”和“锅着火”显然不能公平地各分两分钟，于是引入优先级。锅着火的工作优先级更高。但是如果仍然必须等擦桌子的人主动说“我做完了”，危险仍然来不及处理，因此主管进一步允许高优先级工作直接打断低优先级工作，这就是抢占式调度。

为了以后继续擦桌子，主管必须记录“刚才擦到了哪张桌子”，这相当于上下文；每项工作都有一张记录状态、重要程度和当前进度的档案卡，这相当于TCB；所有已经可以开始但正在等厨师的工作被放在等待执行的队列中，这相当于Ready Queue；墙上的统一时钟每隔固定时间响一次，帮助主管判断某些周期工作是否到时间，这相当于Tick。

这样看，第二章不是一堆互不相关的术语，而是在回答同一个问题：一个CPU面对很多Task时，RTOS如何有规则地分配CPU，并且如何记录和恢复这些Task的运行状态。

## 第二章能够解决什么，又不能解决什么

第二章解决的是“CPU应该怎样在多个Task之间进行分配”的问题。通过合作调度、时间片、优先级和抢占，系统能够让不同Task按照不同实时要求竞争CPU；通过任务队列、TCB和Tick，内核能够真正实现这种调度；通过上下文切换，一个Task被暂停以后能够在未来继续运行。

但是调度机制建立以后会立刻产生新的问题。两个Task都要修改同一个数据怎么办；一个Task拿着某个硬件资源时被另一个Task抢占怎么办；高优先级Task需要的资源恰好被低优先级Task占用怎么办；多个Task都等待对方释放资源又怎么办。

这些问题已经不是单纯“谁获得CPU”能够解决的，而是“多个Task怎样安全地共享资源”的问题。因此第二章之后自然进入第三章的互斥机制。可以把两章的关系理解为：第二章让多个Task能够相互抢占和切换，第三章则必须解决这种并发执行方式带来的共享资源冲突。

## 第二章最终形成的逻辑

第二章可以最终压缩成这样一条路线。

最开始有多个Task，但让它们自己主动交出CPU，这就是合作调度；合作调度过度依赖Task自觉，因此加入时间分片，限制单个Task连续占用CPU的时间；但时间公平不能体现实时任务的重要差异，因此引入优先级；仅有优先级仍然可能让高优先级Task等待低优先级Task主动让出CPU，因此进一步发展为基于优先级的抢占式调度。

抢占发生以后，当前Running Task可能执行到一半被暂停，因此RTOS必须保存它的上下文；为了管理每个Task的状态、优先级、栈等信息，需要TCB；为了快速找到哪些Task已经可以运行，需要任务队列；为了管理周期和延时，需要Tick；而任务之间频繁交叉执行以后，又会出现共享数据竞争和代码可重入等问题。

因此，第一章解决的是“为什么需要RTOS”，第二章解决的是“RTOS最核心的调度器究竟怎样决定现在谁运行”。理解第二章以后，RTOS就不再只是一个抽象的“任务管理软件”，而能够具体理解为：内核不断维护各Task的状态，在某些调度时刻检查Ready任务，并按照调度规则选择最合适的Task使用CPU，同时通过保存和恢复上下文实现Task之间的切换。
