## 引言

第二章解决的是多个Task如何调度，也就是谁先运行、谁后运行、谁可以抢占谁。第三章紧接着解决另一个问题：当多个Task开始访问同一个变量、缓冲区或硬件资源时，如何避免因为交叉执行而把数据或资源状态弄乱。

第三章的总体逻辑如下所示：

```text
多个Task访问共享资源，访问过程可能交叉的问题。
↓
Race Condition
↓
需要Mutual Exclusion互斥来保护数据
↓
最简单使用Flag，但是Flag检查和修改可能被抢占
↓
需要Atomic Operation（原子化操作，也就是两步统一成一步，这样的话，可以解决中间间隔被抢占）
↓
但是，此时会出现taskB，拿不到资源一直检查（出现了Busy Waiting，忙等待）
↓
需要Semaphore(信号量也是原子化操作)，其中二值信号量用于事件/同步，计数信号量用于资源计数，而信号量并没有所有权的问题（信号量确实可能出现“不是自己 Pend，却由自己 Post”的操作），共享资源防止被破坏。
↓
Mutex互斥量具有Ownership并适合资源保护
↓
Semaphore/Mutex需要程序员手工管理，代码复杂后容易遗漏和出错
↓
Monitor可以把共享资源 + 访问方法 + 互斥机制 + 条件等待统一封装
```
下面对于各个历史状态下的相关术语进行说明。
## 简单互斥实现以及弊端
为什么要实现互斥，这个的原因是由于共享资源的多方面调用可能造成数据错乱的问题，下面解释共享资源存在的问题以及简单互斥怎么处理和存在的弊端。
### 共享资源与临界区
共享资源是多个Task都可能访问、修改或使用的对象，例如全局变量、缓冲区、UART、SPI、文件或硬件寄存器。

如果一段代码访问共享资源，而且执行过程中不希望其他Task插进来，这段代码就叫Critical Section，即临界区。
例如：

```c
data.x = new_x;
data.y = new_y;
```

如果x和y必须作为一组完整数据更新，那么就不能出现先更新x、被抢占、另一个Task读到“新x+旧y”的情况。

因此需要Mutual Exclusion，也就是互斥。互斥的本质是：同一个共享资源，同一时刻只允许一个Task进入相关临界区。

### 最简单的方法：单个标志位

最直接的办法是设置一个标志：

```c
if(flag == FREE)
{
    flag = BUSY;

    UseResource();

    flag = FREE;
}
```

其中FREE表示资源空闲，BUSY表示资源正在使用。

但普通Flag并不能天然保证互斥。**问题在于“检查flag”和“修改flag”是两个步骤。**

如果Task A检查到FREE后、还没来得及把flag改成BUSY就被Task B抢占，那么Task B也会看到FREE，并进入资源。Task A恢复以后仍然会按照刚才的判断继续执行，也进入资源。

所以问题不在于Flag只有一个，而在于 **“检查+设置”之间可能被插入其他Task**。
### 原子操作

要解决这个问题，就必须把“检查资源是否空闲”和“把资源设置为BUSY”做成不可分割的操作。

这就是Atomic Operation，即原子操作。

原子操作的含义是：从其他执行者的角度看，这个操作要么还没开始，要么已经完全结束，中间不存在可以被别人插入的状态。

这样Task A一旦完成“检查并设置”，Task B再来时只能看到BUSY。

### 忙等待的问题

即使Flag已经能安全地检查和设置，如果Task拿不到资源时一直这样等：

```c
while(flag == BUSY)
{
}
```

就会形成Busy Waiting，也就是忙等待。

Task虽然没有实际工作可做，却一直占着CPU检查

RTOS更希望的方式是：

```text
资源忙
↓
Task进入Blocked
↓
CPU去运行其他Task
↓
资源释放
↓
Task被唤醒
```

于是引出了Semaphore，也就是信号量。

## 信号量

Semaphore的思想是：由RTOS安全维护一个状态或计数值，Task拿不到许可时不再自己忙等，而是进入Blocked，等许可出现以后再被唤醒。

因此Semaphore既解决了检查与修改的安全性（原子操作），也解决了Busy Waiting的问题。

Semaphore通常分为Binary Semaphore和Counting Semaphore。

### 二值信号量

Binary Semaphore只有0和1两种状态，可以理解为：

```text
0：没有许可
1：有许可
```

它最典型的用途是事件通知和Task同步。

例如CurrentTask要等ADC采样完成：

```text
CurrentTask等待
↓
Blocked
```

ADC完成以后：

```text
ADC ISR
↓
Post Semaphore
↓
CurrentTask被唤醒
↓
Ready
```

所以Binary Semaphore更像一句话：

> “事情做好了，告诉我。”

它适合ADC采样完成、UART数据到达、DMA传输完成、Task A通知Task B等场景。

### 计数信号量

Counting Semaphore可以取0、1、2、3……，用来表示还有多少个同类资源可用。

例如系统有3个缓冲区：

```text
Semaphore = 3
```

每申请一个资源，计数减1；当计数为0时，再申请的Task进入Blocked；资源释放后计数加1，等待Task可以被唤醒。

所以Counting Semaphore解决的是：

> “现在还有几个资源可以用？”

## 互斥量
为什么还需要互斥量呢，这是由于互斥量可以由所属权。
Binary Semaphore只有0和1，看起来也能用来保护一个资源，但Mutex是专门为共享资源互斥设计的。以厨房点单的例子为例：假如初始等待订单：
```C
厨师： Pend(OrderSem)   没有订单  等待

服务员： Post(OrderSem)  “来单了！”
```
这个是由厨师发起，而由服务员释放。
而互斥量来说：他们必须是一个人，就比如厨师炒菜用锅，它只能自己说锅用完了。
Mutex最重要的特点是Ownership，也就是所有权。

所以Mutex表达的是：
> “这个共享资源当前归谁使用。”

而Binary Semaphore表达的是：
> “有没有一个信号或许可。”

因此可以简单区分：

```text
Binary Semaphore
→ 更适合事件通知和同步

Mutex
→ 更适合共享资源保护
```

### Mutex的优先级反转调用

Mutex还能够和实时调度中的优先级机制结合。

例如低优先级Task L已经持有Mutex，而高优先级Task H需要同一个Mutex，那么H只能等待L释放资源。这可能造成Priority Inversion，也就是优先级反转。

因为Mutex知道当前Owner是谁，RTOS可以采用Priority Inheritance，即优先级继承，临时提高L的优先级，让它尽快运行并释放Mutex，然后再恢复原优先级。

因此对于真正的共享变量、UART、SPI等资源保护，Mutex通常比普通Binary Semaphore更合适。

### Semaphore和Mutex存在的弊端

使用Mutex时，程序员通常要写：

```c
MutexLock();

ModifyData();

MutexUnlock();
```

所有访问共享资源的地方都必须记住：

```text
访问前Lock
访问后Unlock
异常路径也要Unlock
```

代码一复杂，就容易出错。

例如：

```c
MutexLock();

if(error)
{
    return;
}

MutexUnlock();
```

如果中间直接return，Mutex没有释放，其他Task可能永久等待。

另外某个Task如果忘记Lock，直接访问共享资源，保护机制也会失效。

所以新的问题不再是“Semaphore和Mutex能不能解决互斥”，而是：

> “这些底层操作要程序员在各处手工维护，太容易遗漏。”

于是进一步引出了Monitor，也就是监视器。

## Monitor监视器
### Monitor监视器的思想
它真正的思想是：

> 把共享资源、访问方法和互斥规则整体封装起来，这样可以减少忘记加锁、忘记解锁、异常路径遗漏以及不同Task使用不同访问规则等人为错误。。

例如：

```text
SharedDataMonitor
│
├── GetData()
├── SetData()
└── 内部自动完成互斥
```

外部Task只调用：

```c
GetData();
SetData();
```

而加锁、解锁以及互斥控制都放在Monitor内部完成。

全、更容易维护。

### Monitor中的条件等待

Monitor还可以配合Condition Variable，也就是条件变量，解决“我已经进入Monitor，但当前条件还不满足”的问题。

例如消费者进入共享缓冲区后发现Buffer为空，如果一直占着Monitor等待，就又会形成忙等待。

因此它可以执行：

```text
Wait(not_empty)
```

然后暂时退出Monitor并进入Blocked。

生产者写入数据以后：

```text
Put(data)
↓
Signal(not_empty)
```

消费者被唤醒。

这样Monitor就能把互斥、等待和唤醒统一组织起来。
