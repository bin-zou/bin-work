# 1-RTOS的特点以及问题解决

## 引言

随着嵌入式系统功能不断增加，任务数量增多，任务之间的执行关系也会越来越复杂。程序最开始只需要按照固定顺序完成少量工作，此时简单循环已经足够；当功能逐渐增加以后，程序会自然发展为超级循环，并通过轮询的方式不断检查不同功能是否需要执行；当系统中出现大量异步事件以后，单纯依靠轮询会带来响应不及时的问题，因此进一步引入中断，让事件主动通知CPU；而当中断数量、任务数量以及任务之间的等待、唤醒和优先关系继续增加以后，仅靠“主循环 + 中断”的方式又会变得难以组织，此时就需要把不同功能拆分成独立任务，并由RTOS统一管理这些任务的执行。

这条演化路线可以概括为：简单循环 → 超级循环/轮询 → 中断驱动 → RTOS多任务调度。

其中需要先区分两个概念。功能回答的是“程序要做什么”，例如电流采样、电流控制、串口通信和故障检测；执行机制回答的是“这个功能什么时候执行、由谁触发执行”。同一个电流控制函数既可以放在 `while(1)` 中循环调用，也可以放在ADC中断中执行，还可以作为RTOS任务的一部分由调度器安排执行。随着系统复杂度增加，真正变难的往往不是某个功能本身，而是这些功能之间“谁什么时候执行”的关系。

## 简单循环

对于非常简单的系统，如果工作内容固定而且执行顺序始终不变，那么使用简单循环即可。例如一个程序始终重复“采样—控制—输出”，可以直接写成：

```c
while(1)
{
    Sample();
    Control();
    Output();
}
```

它的特点是执行顺序完全固定，CPU始终按照同一条路线重复运行。餐馆中可以把它理解为只有一个厨师，而且每天只做一种固定流程的工作，例如“接单—煮面—端菜”。因为没有其他并行的事情，也不存在不同任务之间的时间冲突，所以根本没有必要引入复杂的调度机制。

这种方式最大的优点是简单，程序员能够直接看出下一步会执行什么，程序结构和执行关系几乎是一一对应的。它适用于功能数量很少、执行顺序固定、对异步事件响应要求不高的简单嵌入式程序。

它的问题在于，一旦功能增加，所有事情就不能再简单地沿着一条固定路线完成。例如除了控制之外还加入通信、显示和故障检测，不同功能又可能具有不同的执行周期，这时简单循环就开始不足，因此程序自然发展为超级循环。

## 超级循环/轮询

超级循环是在一个大的 `while(1)` 中依次放入多个功能，让CPU一圈一圈地执行。例如：

```c
while(1)
{
    CurrentControl();
    PositionControl();

    if(UART_DataReady())
    {
        UART_Process();
    }

    FaultCheck();
    Display();
}
```

这里的执行机制仍然是顺序循环，只不过一圈中包含了多个功能。餐馆中可以理解为一个厨师现在同时负责煮面、炒饭、烧水和做汤，他按照一定顺序不断检查和处理这些事情。

当某件事情并不是每一圈都需要处理时，就会出现轮询。轮询的含义是CPU主动检查某个事件是否已经发生。例如程序每执行一圈都会判断一次 `UART_DataReady()`，如果数据没有到，就继续执行其他功能，下一圈再回来检查。它和忙等待不同。忙等待是：

```c
while(UART_DataReady() == 0)
{
}
```

这表示CPU一直停在这里反复询问“数据到了吗”，在条件满足之前后面的代码无法执行；轮询则是“问一次，如果没有就先去做别的，下一圈再回来问”。因此可以把忙等待理解为“站在原地一直问”，把轮询理解为“走一圈回来问一次”。

餐馆中，烧水就是一个很直观的例子。厨师并不知道水什么时候烧开，所以每隔一段时间去看一下“水开了吗”，没开就继续做其他菜，过一会儿再回来检查。这就是轮询。

超级循环和轮询的优点是仍然比较简单，不需要操作系统，程序员可以直接控制执行顺序和检查频率。对于任务数量不多、实时性要求一般的系统，它完全可以工作。

它的主要问题是响应时间取决于“什么时候轮到检查这个事件”。假设UART数据刚刚到达，但程序刚好开始执行一整圈其他功能，那么它必须等到CPU再次运行到UART检查位置时才能被发现。因此功能越多、某些功能执行时间越长，轮询的最坏响应时间越难保证。

轮询真正不能很好解决的问题是：某个异步事件发生以后，能不能不等CPU下一次主动检查，而是在事件发生时马上告诉CPU。我们真正希望的并不是“不断去问好了没有”，而是“我先做其他事情，好了以后你主动告诉我”。为了实现这种执行方式，就引出了中断。

## 中断驱动

中断的核心变化是把“CPU主动找事件”变成“事件主动找CPU”。以UART为例，轮询时CPU需要不断检查UART是否收到数据；使用中断以后，UART收到数据时由硬件产生中断请求，CPU暂时停止当前执行流程，进入对应的中断服务程序进行处理，完成后再返回原来的程序继续执行。

```c
interrupt void UART_ISR(void)
{
    ReadUART();
    ClearInterruptFlag();
}
```

这里的 `ISR` 是 Interrupt Service Routine，即中断服务程序，表示中断发生以后专门执行的代码。

餐馆中可以把中断理解为给水壶安装一个响铃。以前厨师必须不断去检查水是否烧开，现在水烧开以后水壶自己“叮”一声，厨师听到以后暂停当前工作，处理水壶，然后继续原来的事情。这样就不再需要不停轮询水壶。

中断最大的优点是提高了对异步事件的响应能力。ADC采样完成、UART接收、CAN接收、定时器到时、外部故障信号等，都非常适合通过中断及时通知CPU。

中断出现以后，程序执行顺序不再完全固定。例如主程序执行到一半时可能突然进入UART中断，处理完后再返回原来的位置继续执行。从整体上看，好像主程序和不同事件同时在推进，但对于单核CPU来说，任意一个瞬间仍然只执行一个程序。这种“看起来多个事情同时推进，但实际上CPU在不同执行流之间快速切换”的现象，可以称为准并发。

中断解决了“事件如何及时通知CPU”的问题，但它并没有解决整个复杂系统的组织问题。当ADC、PWM、UART、CAN、定时器和故障中断越来越多时，程序会出现大量中断服务程序，甚至发生中断嵌套。如果又把电流控制、速度控制、通信处理和故障检测等完整功能都塞入中断服务程序，那么功能逻辑、执行时机和中断逻辑会逐渐混在一起。

这就是“功能和执行机制纠缠”的含义。例如 `CurrentControl()` 本身只是完成电流控制这一功能，但如果它什么时候执行、执行几次、和通信谁先谁后、是否被其他中断打断等关系全部依附在某个ISR内部，那么程序越复杂，执行关系就越难维护。

因此，中断主要解决的是“事件来了以后怎么快速响应”，但它不能天然解决“系统里有很多独立功能时，谁应该先执行、谁应该等待、谁应该被唤醒、某个功能暂时没事做时怎么办”等更高层的问题。这就引出了RTOS。

## RTOS

RTOS的基本思路是把系统中的不同功能拆成相对独立的任务，例如 `CurrentTask`、`PositionTask`、`UARTTask`、`FaultTask` 和 `DisplayTask`，然后把“现在到底应该运行哪个任务”的问题交给调度器统一管理。

Task可以理解为一个相对独立的软件工作单元。Scheduler即调度器，它负责从当前可以运行的任务中决定谁获得CPU。对于单核处理器来说，即使存在很多Task，任意时刻CPU仍然只能真正执行其中一个，因此必须有统一的调度规则。

RTOS相比“主循环 + 中断”更重要的能力之一，是能够自然表达“等待”。以UART任务为例，如果当前根本没有收到数据，那么这个任务即使获得CPU也没有任何事情可做。裸机程序通常需要通过轮询、标志位或状态机自己实现这种等待关系，而RTOS可以直接让任务进入Blocked状态。

Blocked表示任务正在等待某个条件，此时即使给它CPU也没有意义。例如UART任务正在等待数据、周期任务正在等待下一控制周期，都可以进入Blocked。任务进入Blocked以后，CPU不会跟着一起等待，而是去运行其他已经具备执行条件的任务，因此“Task等待”并不等于“CPU等待”。

当UART数据真正到达时，硬件仍然可以产生中断，中断服务程序负责通知RTOS，使UART任务从Blocked变成Ready。Ready表示任务已经具备运行条件，但CPU可能正在运行其他任务；当调度器最终选中它以后，它才进入Running。Running表示该任务当前正在真正使用CPU。

因此，RTOS中最基本的状态关系可以理解为：任务因为等待某个条件进入Blocked；条件满足以后变成Ready；调度器选中以后变成Running。

这里也能看出，中断和RTOS不是替代关系。中断仍然负责快速响应硬件事件，而RTOS负责管理更复杂的软件任务。典型过程是：硬件事件发生 → 产生中断 → ISR通知RTOS → 某个Task由Blocked变成Ready → Scheduler重新判断当前应该运行哪个Task。

继续使用餐馆例子，当餐馆规模变大以后，厨师需要同时面对炒菜、煮面、外卖、电话、烧水等大量事情。给所有设备安装铃只能解决“事情发生以后及时提醒厨师”，但厨师依然需要判断“现在先处理谁”。此时可以引入一个厨房主管，由主管根据事情的重要程度和当前状态决定下一步让厨师处理哪项工作。各项工作相当于Task，厨房主管相当于Scheduler，而整个厨房的统一管理规则就相当于RTOS。

因此，RTOS真正解决的核心问题不是单纯让CPU“跑得更快”，而是在复杂嵌入式系统中统一管理多个任务的执行关系，让不同周期、不同事件触发条件以及不同重要程度的任务能够有组织地共享CPU。

RTOS同样不是万能的。它不能凭空增加CPU算力，也不能让一个本来需要2 ms完成的算法突然在500 μs内完成，更不能自动保证所有任务都满足时间要求。它提供的是任务划分、调度、等待、唤醒以及后续同步和通信等机制；至于任务优先级是否合理、计算量是否超过CPU能力、最坏响应时间是否满足要求，还需要进一步分析。

这一章最核心的演化逻辑因此可以压缩为：简单循环适合固定而少量的功能；功能增加以后发展为超级循环，并通过轮询主动检查事件；轮询对异步事件的响应受到循环周期限制，因此引入中断，让事件主动通知CPU；而当功能、中断和等待关系进一步复杂以后，仅靠主循环和ISR难以组织，于是把功能任务化，并使用RTOS的调度器统一管理多个Task的执行。
